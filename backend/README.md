# Backend — Secure Accounts Lab

FastAPI + SQLAlchemy + PostgreSQL, JWT (HS256), passwords hashed with Argon2id (`pwdlib`).

## Running

Whole stack in Docker: see the [root README](../README.md). Local development:

```bash
# from the repository root — starts Postgres (localhost:5433) and Mailpit (SMTP 1025, UI 8025)
docker compose up -d db mailpit

cd backend
cp .env.example .env   # and set JWT_SECRET
uv sync
uv run fastapi dev app/main.py
```

- Swagger: http://localhost:8000/docs (click **Authorize** and paste the `access_token`).
- Mailpit inbox (all outgoing emails): http://localhost:8025

On startup the tables are created automatically and an admin is added from `ADMIN_EMAIL` / `ADMIN_PASSWORD`.
There are no migrations: after a model change, recreate the database with `docker compose down -v && docker compose up -d`.

## Password policy (task 1)

At least 8 characters, an uppercase and a lowercase letter, a digit and a special character. Checked on
registration, password change and password reset (`app/core/password_policy.py::password_policy_errors`);
violations are returned as a list with 422.

Password change is confirmed by email:

1. `POST /users/me/password {current_password, new_password}` checks the current password and the policy, rejects
   reusing it, stores the hash of the new password in a pending challenge and emails a 6-digit code (202).
2. `POST /users/me/password/confirm {code}` checks the code (same expiry and attempt limit as 2FA codes), applies
   the new hash and sets `password_changed_at`, which invalidates every token issued before. The response contains
   a fresh access token so the current session continues, and a "password was changed" email is sent.

## CAPTCHA on registration (task 2)

`GET /auth/captcha-config` tells the frontend which provider is used (`CAPTCHA_PROVIDER`). Registration is
refused with 400 if the check fails. `CAPTCHA_ENABLED=false` turns the check off.

**`image` (default)** — a classic text CAPTCHA generated by the backend (`captcha` library, Pillow):

1. `GET /auth/captcha` returns `{captcha_id, image, expires_in}`: a PNG (data URI) with `CAPTCHA_LENGTH` random
   distorted characters (ambiguous `0/O/1/I/L` excluded). Only an HMAC of the answer is stored, in
   `captcha_challenges`, and it expires after `CAPTCHA_EXPIRE_MINUTES`.
2. `POST /auth/register` sends `captcha_token` = `captcha_id` and `captcha_answer` = the typed text
   (case-insensitive). Each challenge is single-use: it is deleted on the first check, right or wrong, so a
   wrong answer means loading a new image.

**`turnstile` / `recaptcha`** — third-party widgets (Cloudflare Turnstile, Google reCAPTCHA v2). The widget's
token goes to `captcha_token`, and the backend checks it at the provider's `siteverify` endpoint with
`CAPTCHA_SECRET_KEY` and the client IP. Set `CAPTCHA_SITE_KEY` / `CAPTCHA_SECRET_KEY` from the provider's
dashboard (with `localhost` as a domain).

## Account activation (task 3)

After registration an email with a link `FRONTEND_URL/activate?token=...` is sent. The token is random
(`secrets.token_urlsafe`), stored only as a SHA-256 hash, single-use and expires after
`ACTIVATION_TOKEN_EXPIRE_MINUTES`. The frontend sends it to `POST /auth/activate`. Login is refused until
the account is activated; `is_verified` is shown in the profile.

## Brute-force protection and login log (task 4)

- After `MAX_FAILED_LOGIN_ATTEMPTS` wrong passwords in a row the account is locked for `LOCKOUT_MINUTES` (423).
- More than `IP_MAX_FAILED_ATTEMPTS` failures from one IP within `IP_WINDOW_MINUTES` → 429 for that IP.
- Every login attempt is logged (email, user, IP, user agent, method `password`/`google`, result, time). Results: `success`,
  `invalid_credentials`, `locked`, `blocked`, `not_verified`, `ip_throttled`, `mfa_pending`, `mfa_failed`.
- Admin sees the log (`/admin/login-attempts` with filters by email, user, IP, result), per-email
  stats (`/admin/login-attempts/summary`), and can block/unblock accounts. Unblocking also clears a lockout.
  A blocked user's existing tokens stop working immediately.

## Two-factor authentication (task 5)

Email one-time code (6 digits, `secrets.randbelow`), valid for `MFA_CODE_EXPIRE_MINUTES`, single-use,
at most `MFA_MAX_ATTEMPTS` wrong tries per code. Only an HMAC of the code is stored.

- Enable: `POST /users/me/mfa/enable` sends a code, `POST /users/me/mfa/confirm {code}` turns 2FA on.
- Disable: `POST /users/me/mfa/disable {password}`.
- Login with 2FA: `POST /auth/login` returns `{mfa_required: true, mfa_token}` instead of a JWT and emails
  a code; `POST /auth/login/mfa {mfa_token, code}` returns the JWT.

## Sign in with Google (task 6)

OpenID Connect Authorization Code flow with PKCE:

1. The frontend opens `GET /auth/google/login` (a plain link, not fetch). The backend generates `state`,
   `nonce` and a PKCE `code_verifier`, stores them in a signed short-lived HttpOnly cookie and redirects
   to Google.
2. Google redirects back to `GET /auth/google/callback?code=...&state=...`. The backend checks `state`
   against the cookie, exchanges the code (with `code_verifier` and the client secret) for an `id_token`
   and verifies it: RS256 signature against Google's JWKS, `iss`, `aud`, `exp`, `nonce`, `email_verified`.
3. The user is found by Google `sub`, otherwise linked by email, otherwise created (already activated).
   Blocked users are refused; if 2FA is enabled an email code is required as usual.
4. The backend redirects to `FRONTEND_URL/oauth/callback#access_token=...&token_type=bearer&expires_in=...`,
   or `#mfa_token=...` (then `POST /auth/login/mfa`), or `#error=...`.

### Google Cloud setup

1. https://console.cloud.google.com → create (or pick) a project.
2. **Google Auth Platform** (https://console.cloud.google.com/auth/overview) → *Get started*: app name,
   support email, audience *External*, contact email.
3. **Audience** → *Test users* → add the Google accounts you will sign in with (needed while the app is
   in *Testing*).
4. **Clients** → *Create client* → type *Web application*, *Authorized redirect URIs*:
   `http://localhost:8000/auth/google/callback`. Copy the client ID and secret right away (or download the
   JSON) — the secret is shown in full only once.
5. Put them into `backend/.env` (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) and restart the backend
   (`docker compose up -d backend` re-reads `.env`).

Without them `/auth/google/login` redirects to the frontend with `#error=Google login is not configured on the server`.

## Password reset (task 7)

`POST /auth/password-reset/request {email}` always answers 202 (no account enumeration) and emails a link
`FRONTEND_URL/reset-password?token=...` (single-use, hashed, expires after `PASSWORD_RESET_TOKEN_EXPIRE_MINUTES`).
`POST /auth/password-reset/confirm {token, new_password}` checks the password policy, sets the new password,
clears a lockout and invalidates all JWTs issued before the change.
